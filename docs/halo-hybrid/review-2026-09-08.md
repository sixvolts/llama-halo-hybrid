# llama-halo-hybrid review — final report

Read-only review of `/home/sixvolts/llama.cpp` (main, 136 commits over merge-base `9a4843cf2`). Seven reading passes (HIP kernels, scheduler/RPC, core llama, models/conversion, server, perf levers, hygiene), every finding independently re-read by a second pass. Nothing was executed. Severities below are post-verification.

## 1. Executive summary

- **One high survives.** At `n_copies==1` the scheduler's write-after-read guard for cross-backend input copies degraded from upstream's host `ggml_backend_synchronize(split_backend)` to a same-stream no-op `event_wait` once the fork started creating events for local GPU backends (`ggml/src/ggml-backend.cpp:1836-1841`, `2210-2216`); eager copies widen the window further. Both production layouts run it; no corruption has been observed (lanes greedy output byte-identical at 4K), so it is a confirmed latent race, not a confirmed corruption.
- **Kernels and model ports hold up.** Of 14 refuted items, most were high/medium perf or bug claims against the HIP kernels, the pair schedule, the RPC drains and the GLM graph; each fell to reading (unreachable path, wrong kernel attributed, unmeasured cost, or upstream-inherited). The one kernel bug confirmed (`fattn-mma-f16.cuh:1747` tile_Q barrier) is pre-existing upstream and the fork's change strictly shrank it.
- **Documentation is the weakest area.** Six confirmed false or contradictory claims in `HALO-HYBRID.md`/`README.md` (retired-switch sentence, #28118 item and its table row, GLM branch label, `-ot` rule, ON_DEVICE checkpoint claim, stale event row), plus two undocumented env vars and residual `ep_zero_row` code that contradicts the doc's "LLAMA_EP dropped" statement.
- **Test coverage gaps on shipped paths.** Split-J Q8_0 J=128 and all six MMQ register-prefetch specializations are reachable only behind `TBO_GLM_EVAL`; neither `graph_mtp` head is ever constructed by any test; both production layouts run a draft head.
- **Performance headroom by reading is small.** The only structural lever with a large ceiling (async remote result fetch, +33-45% two-host prefill) is gated on solving the lanes+draft decode collapse, whose root cause the code does not reveal; the best-evidenced medium wins are `llm_graph_input_kpool::can_reuse` (glm5next rebuilds its graph every step) and an MMQ activation-quantize cache (~1.7-2% prefill, unmeasured).

## 2. Confirmed findings

### Scheduler / RPC

**[sched-rpc#2] HIGH — Cross-backend input copies have no destination-side ordering at n_copies==1; eager copies widen the window**
`ggml/src/ggml-cuda/ggml-cuda.cu:2608` · `ggml/src/ggml-backend.cpp:1836-1841`, `2210-2216`, `1999-2031`, `1482-1485`, `1587-1590`
Evidence: `ggml_backend_cuda_cpy_tensor_async_impl` orders the source stream after the destination's queued work only under `static const bool lazy_inputs = getenv("GGML_SCHED_LAZY_INPUTS") != nullptr;` (ggml-cuda.cu:2608-2620), which HALO-HYBRID.md:60 records as off ("net loss on ROCm"). The peer copy runs on `cuda_ctx_src->stream()` (2630/2633); `cpy_tensor_async_nowait` (2658-2660) passes `wait_dst=false`, so an eager copy has no ordering in either direction against the destination. Upstream's guard at n_copies==1 was the `else` branch `ggml_backend_synchronize(split_backend)` at ggml-backend.cpp:1836-1841 (merge-base created events only `if (sched->n_copies > 1)`, 9a4843cf2:1909); the fork now creates events for any local GPU backend at n_copies==1 (2210-2216), so the `event_wait` branch runs instead — a wait on `split_backend`'s own stream for an event recorded on that same stream, i.e. a no-op. Split input copies are ordinary ggml-alloc-reused tensors: the `set_input/set_output` no-reuse flags at 1482-1485 are gated on `n_copies > 1`, and `input_cpy` is allocated at the *consumer* split's position (1587-1590) while eager copies (1999-2031) write it at the producer split. Reconciles with the refuted perf-levers#3: both readers agree the line at 1836 is unmodified and the `event_wait` is a self-wait; the regression is which branch is taken, not the text. Not shown: an actual aliasing instance in these graphs; HALO-HYBRID.md:198 reports lane output byte-identical to single-lane at 4K.
Proposal: make `ggml_backend_cuda_cpy_tensor_async_impl` always record a destination-stream event and have the source stream wait on it (drop the `lazy_inputs` gate; cover the same-physical-device branch at 2602-2603), or restore a destination-side guard in the scheduler that is not a same-stream no-op. Residual gap for eager copies: consumer splits with intervening destination-backend splits are still unprotected — restrict the eager loop to consumers with no intervening destination split, or mark eager-copied `input_cpy` tensors set_input/set_output (costs compute-buffer size, removes aliasing entirely). Validate by instrumenting ggml-alloc offsets of eager-copied `input_cpy` under the Qwen3.8 `LLAMA_PREFILL_LANES=2` layout for overlap with tensors whose last use is an earlier destination split; measure the cost of the event wait before shipping, since a producer-stream wait on the destination queue is plausibly what made `GGML_SCHED_LAZY_INPUTS` a net loss and it risks the +30-45% prefill that eager copies buy.
Effort: hours (fix), plus measurement.

**[sched-rpc#3] MEDIUM — GRAPH_COMPUTE/GRAPH_RECOMPUTE now expect a reply, but the protocol version is unchanged; mismatched peers hang or abort**
`ggml/include/ggml-rpc.h:9`
Evidence: `git diff 9a4843cf2..HEAD -- ggml/include/ggml-rpc.h` is empty (still `RPC_PROTO_MAJOR_VERSION 6 / MINOR 0 / PATCH 0`). Client ggml-rpc.cpp:1027-1037 passes `&graph_done, 0`; server ggml-rpc.cpp:2031/2045 replies `send_msg(sock, &done, 0)`. `rpc_dispatcher::work()` gates the reply read on the output *pointer* (ggml-rpc.cpp:565-566), so a fork client against an upstream 6.0.0 server passes `negotiate_hello` (356: only `major !=` and `minor >` are checked; patch never compared) and blocks forever in `recv_data(&out_size, 8)` — no socket timeout exists. The reverse pairing desyncs on the extra 8-byte prefix and hits `RPC_STATUS_ASSERT` -> `GGML_ABORT`. `rpc_msg_hello_req` carries only `conn_caps` (89-91), so neither side can detect the mismatch. HALO-HYBRID.md:262-263 says "both peers must run this tree"; nothing enforces it.
Proposal: bump `RPC_PROTO_MAJOR_VERSION`. Do **not** put a flag in `conn_caps`: it is exactly 24 bytes, fully consumed by `rdma_caps` (transport.cpp:117-122, static_assert), and `update_caps` treats any nonzero byte as "peer has RDMA" (transport.cpp:591-598), so a TCP-only peer would fail RDMA activation.
Effort: minutes.

**[sched-rpc#4] MEDIUM — No TCP keepalive on the RPC control socket; the empty-reply change puts a blocking receive on every graph**
`ggml/src/ggml-rpc/transport.cpp:445`
Evidence: `rdma_poll` (transport.cpp:425-452) has no deadline; its only non-completion exit is `if (s > 0 && ((spinning && (s & 0xFFFFF) == 0) || (!spinning && (s & 0x3FFF) == 0))) { if (tcp_peer_closed()) { return false; } }`, and `tcp_peer_closed` (201-210) is a zero-timeout `poll` for `POLLHUP|POLLERR|POLLRDHUP` — sees FIN/RST, not a powered-off host. `grep` for `SO_KEEPALIVE|TCP_KEEP|SO_RCVTIMEO` in ggml/src/ggml-rpc/ hits nothing (only `TCP_NODELAY` at 667 and `SO_REUSEADDR` at 673). Merge-base sent GRAPH_COMPUTE fire-and-forget; the fork's `send_async(..., &graph_done, 0)` (ggml-rpc.cpp:1030-1037) makes the dispatcher block in `recv_data` for the whole remote graph, and with no further send the QP retry timeout (transport.cpp:400-402) that would otherwise surface a dead peer as `IBV_WC_RETRY_EXC_ERR` is never reached. HALO-HYBRID.md:339-341 already records the server-side half as open.
Proposal: set `SO_KEEPALIVE` + `TCP_KEEPIDLE/KEEPINTVL/KEEPCNT` (e.g. 30 s / 10 s / 3) in `socket_t::connect` and `socket_t::accept` (transport.cpp:677-689). A poll-loop deadline is the wrong fix (long prefill graphs). Note the client's only reaction to a detected dead peer is `GGML_ABORT` (ggml-rpc.cpp:35, 566) — this converts a hang into a fast abort, not recovery.
Effort: hours.
